# Calup Frontend, UI and Design Review

Reviewed **23 October 2026** using Impeccable 3.8.0, design-taste-frontend and freshly fetched Vercel Web Interface Guidelines. **Review only: no application changes.**

## Conclusion and evidence boundary

Preserve Calup's lime/black identity and established typography. The first work should improve trustworthy task completion: visible errors inside dialogs, consistent rescheduling eligibility, accurate refund progress, zoom and keyboard access. A redesign is premature while these interaction contracts disagree.

Assessment A completed independently before Assessment B's detector findings were released. Scanners covered **136 source files**, including 64 JSX and 32 CSS files; manual inspection covered every route family and shared foundations, not every branch line by line. The browser inventory exposed no apps or browsers. Therefore this report does **not** certify visual polish, mobile clipping, WCAG compliance, live payments, deployed behavior or authenticated workflows. Historical screenshots are not current verification.

Production build passed: 2,071 modules, 49 manifest entries and **63 referenced files, none missing**. Bundle warnings remain. No database, provider transaction, notification or user account was modified.

## Priority findings

Priorities: P0 = demonstrated critical blocker; P1 = high-impact exclusion or task/trust failure; P2 = important recovery/consistency defect; P3 = polish/maintenance. **No P0 was demonstrated.** Source evidence can establish a conflicting contract without proving every browser symptom.

### P1 — Errors can disappear behind native dialogs

[AccessibleModal.jsx](../../frontend/src/components/ui/AccessibleModal.jsx) calls `showModal()` at line 13. [NotificationViewport.jsx](../../frontend/src/components/ui/NotificationViewport.jsx) portals notifications to the body at lines 19–30. Ordinary body content cannot rise above the native modal top layer, even with the viewport's very high z-index.

[Services.jsx](../../frontend/src/pages/dashboard/Services.jsx), lines 45, 296–300 and 529, discards local submission-error display and reports failed saves through a global toast while its dialog stays open. [TicketPanel.jsx](../../frontend/src/components/support/TicketPanel.jsx), lines 41, 59 and 85, uses the same outside-dialog failure channel inside SupportWidget's native dialog.

**Effect:** a failed save can appear unresponsive and its recovery message is outside the active interaction context. **Fix:** retain form-local errors inside the active dialog, associate them with fields or the submit summary, and make shared feedback modal-aware. Increasing z-index is insufficient. Suggested command: `$impeccable harden`.

### P1 — Customer rescheduling disagrees with server policy

[CustomerBooking.jsx](../../frontend/src/pages/booking/CustomerBooking.jsx), lines 348–358, 647–649 and 1805–1820, gates rescheduling using `cancellationWindow` and browser-local timing. [publicBookings.js](../../backend/server/routes/publicBookings.js), lines 1120–1145, enforces the booking snapshot's `reschedule_min_hours_before` and `max_reschedules` instead.

**Effect:** valid changes can be blocked, or a customer can select a slot before an inevitable rejection. A 12-hour cancellation cutoff versus a 24-hour reschedule cutoff permits a doomed attempt 18 hours before the appointment. **Fix:** expose authoritative eligibility, remaining customer changes and deadline from the accepted booking policy, including merchant timezone. Keep merchant-initiated changes separate from the customer's allowance. Suggested command: `$impeccable harden`.

### P1 — Mobile zoom is explicitly restricted

[frontend/index.html](../../frontend/index.html), line 10, specifies `maximum-scale=1.0, user-scalable=no`.

**Effect:** browsers honoring these flags restrict customers who need magnification. **Fix:** retain normal responsive viewport sizing and remove the zoom restrictions; verify pinch zoom and 200% text/reflow. This is an accessibility risk, not a claim that all browsers honor the flags. Suggested command: `$impeccable harden`.

### P1 — Existing account navigation excludes keyboard users

[DashboardLayout.jsx](../../frontend/src/layouts/DashboardLayout.jsx), lines 226–230, makes the live avatar a click-only `div` that navigates to settings.

**Fix:** use a named settings link for this existing affordance, with visible focus. The commented-out alternative is inactive. Repair semantics without restoring the user's intentionally disabled extra navigation. Suggested command: `$impeccable harden`.

### P2 — Refund wording overstates financial progress

[CustomerBooking.jsx](../../frontend/src/pages/booking/CustomerBooking.jsx), lines 841 and 855, promises to initiate a full refund and reports it initiated. [refundService.js](../../backend/server/services/refundService.js), lines 55–140, records a `refund_due` obligation rather than transferring money. Later customer copy at lines 1322–1324 correctly says the merchant must send the refund directly.

**Fix:** use “Full refund recorded as due” for this path and state who must act next. Reserve “submitted to Cashfree,” “sent” and “received” for their actual evidence. Do not confuse this legacy/manual path with every separate Cashfree refund route. Suggested command: `$impeccable clarify`.

## Design, typography and information hierarchy

**Anti-pattern verdict:** source suggests a coherent Calup identity, not a reason to replace the brand. Whether the rendered composition feels generic cannot be honestly judged without screenshots. Keep lime for primary action/selection, clear ink for operational values, and semantic color for status. Public marketing may be more expressive than the working dashboard.

Three declared font roles—Plus Jakarta Sans headings, Instrument Serif accents and Inter body—need consistent boundaries, not a random replacement to satisfy a scanner. Preserve current identity; review redundant font loading during performance work. Prefer readable operational labels over widespread 10–11px context text. Small text alone is not a proven WCAG failure.

Reduce decorative gradients/glass in working screens when they compete with scheduling and money. Examples worth inspecting are the zero-services banner (Overview.jsx:53), subscription time card (Subscription.css:18), and tracked small labels (Subscription.css:12). These are taste/consistency observations, not independently verified accessibility failures.

Keep one obvious next task per onboarding state. Integration search/filtering is useful only if the configured tools justify the extra choices. On operational pages, group actions by service, instructor, date and financial state; avoid animating a newly refreshed real value through invented intermediate totals.

## Personas, cognitive load and trust

- **Merchant on a phone:** needs a publishable service and dependable instructor schedule. Silent loading and ambiguous partial saves increase uncertainty. Keep the schedule result and save scope explicit.
- **Customer changing an appointment:** should not learn cancellation-policy internals to discover reschedule eligibility. Show the permitted window and remaining changes before choosing another slot.
- **Customer worried about money:** needs payment received, appointment confirmed, refund due, provider processing and refund received to remain distinct. Financial wording is part of transaction safety.
- **Keyboard/screen-reader user:** needs one predictable dialog contract, available in-context feedback and shell bypass; the current native modal is a good base.
- **Support/refund operator:** benefits from evidence freshness and honest provider-health distinctions. Dense small labels and hidden feedback increase working-memory demands.

## Strengths to retain

Policies prevents editing after failed loading and supports retry, field associations and first-invalid focus. Booking details provide labels, autocomplete and associated errors. Payment status distinguishes money received from appointment fulfillment and warns against paying twice. Analytics offers table alternatives. Live appointments preserve the last successful snapshot and explain stale data. Commerce discloses sandbox/incomplete delivery. These patterns should become shared standards.
